# Log File Analysis Portfolio

This cybersecurity portfolio presents a comparative analysis of Windows and Linux log files, the tools used to review them, and the security events produced by scripted system changes. The project was completed for **IS-6303: Voice and Data Security** on **April 19, 2025**.

The portfolio focuses on how log data can be used to reconstruct system activity, identify unusual behavior, and recognize events that may indicate unauthorized access or system compromise.

## Why the Project Was Completed

System and security logs contain details about events such as login attempts, account activity, file access, configuration changes, errors, shutdowns, and privilege use. Reviewing this information supports troubleshooting, system administration, security auditing, and digital-forensics work.

The project was completed to examine how Windows and Linux organize log data, compare available log-analysis tools, and analyze activity generated by scripts on both operating systems. Particular attention was given to events that could become security concerns when they occur without authorization, including new account creation, password changes, privilege escalation, remote command execution, and attempts to remove evidence.

## Tools and Technologies

### Windows Event Viewer

Windows Event Viewer was used to examine Windows event logs and create a custom view around the time the scripts were executed. The tool organizes records by event level, source, date, event ID, and task category. Relevant records included PowerShell activity, User Account Management events, local group changes, and remote command warnings.

### KSystemLog

KSystemLog was used to review Linux activity through a graphical interface. It organizes records into categories such as authentication, daemon, kernel, system, cron, boot, and Apache logs. Its filtering, highlighting, and visible event descriptions made the sequence of script-generated changes easier to follow.

### `journalctl` and `systemd-journald`

Linux logging concepts included `systemd-journald`, which stores structured journal data, and `journalctl`, which displays that data in the terminal. Linux priority levels discussed in the project included emergency, alert, critical, error, warning, notice, informational, and debug.

### Splunk

Splunk was reviewed as a security information and event management platform. Its capabilities include centralized data collection, indexing, searching, dashboards, alerts, visualizations, long-term log retention, and detection of activity such as brute-force attempts, privilege escalation, lateral movement, and data exfiltration. Cost and increasing data volume were identified as possible limitations.

## What the Work Involved

The first stage examined the purpose and organization of Windows and Linux logs. Windows stores common event logs as `.evtx` files and presents categories such as Application, Security, Setup, System, and Forwarded Events. Linux uses `systemd-journald` for centralized journal storage and provides `journalctl` for terminal-based access.

The second stage compared Windows Event Viewer, KSystemLog, and Splunk. The comparison considered operating-system support, filtering, real-time monitoring, organization, accessibility, cost, alerting, and suitability for local or enterprise analysis.

The final stage involved running scripts on Kali Linux and Windows, locating the events created by those scripts, and evaluating their possible security significance. Linux activity was reviewed through KSystemLog, while Windows activity was examined through a custom Event Viewer view. A Base64-encoded PowerShell script was also decoded to determine the actions performed during the second Windows script.

## Key Findings

### Linux Activity

The first Kali Linux script created four users and four corresponding groups: **Tyler, Dade, Elliot, and Thomas**. Passwords were changed for the new accounts, and Elliot and Thomas received elevated privileges through membership in the `sudo` group.

The second Kali Linux script removed the four users and their groups. Elliot and Thomas were removed from the `sudo` group, and the script deleted itself. These actions could be legitimate when authorized, but unexpected account creation and administrative privilege assignment would be significant warning signs.

### Windows Activity

The first Windows script created and enabled the same four accounts, reset their passwords, changed permissions, checked group membership, and added users to security-enabled local groups. Elliot and Thomas received administrator privileges.

The second Windows script generated warnings associated with remote command execution. The encoded PowerShell content removed the accounts created by the first script, deleted their profiles and privileges, cleaned up logs, cleared PowerShell history, and exited. Remote execution, User Account Management events, encoded commands, log cleanup, and command-history removal could indicate an effort to hide unauthorized activity.

### Tool Comparison Outcome

KSystemLog provided the clearest view of the Linux script activity because event descriptions and timestamps were visible without opening each record individually. Windows Event Viewer contained the necessary information but made it more difficult to separate script-generated events from normal background activity. Splunk offered the strongest capabilities for high-volume, cross-platform, enterprise monitoring, but its cost can make it less practical for smaller environments.

## Repository Sections

### `docs/`

The `docs` directory contains the summarized written documentation for the project. Each file focuses on a different part of the log-analysis process.

- `findings.md` documents the security-relevant activity identified in the Windows and Linux logs, including account creation, password changes, privilege escalation, remote command execution, and cleanup behavior.
- `methodology.md` explains the scope of the project, the evidence used, the analysis process, platform-specific review methods, and the limitations of the work.
- `tool-comparison.md` compares Windows Event Viewer, KSystemLog, and Splunk based on platform support, usability, filtering, monitoring, cost, scalability, and appropriate use cases.

### `full-report/`

The `full-report` directory contains the sanitized version of the original lab report.

- `sanitized-lab-report.pdf` provides the original project narrative, technical background, analysis, findings, figures, and references while removing personal or identifying information that should not appear in a public repository.

The `images` directory contains screenshots and figures extracted from the original report.

These images provide visual evidence of the logging tools, account activity, Windows events, Linux events, cleanup behavior, and encoded PowerShell content discussed throughout the project documentation. The filenames describe the activity shown in each image so they can be easily referenced.
